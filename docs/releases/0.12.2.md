# Poly 0.12.2 — Prepared plans and driver-contributed add façades

Status: **validated**. The authoritative scope and acceptance criteria are
maintained in [the roadmap](../../ROADMAP.md#0122--prepared-plans-and-driver-contributed-add-façades).

## Purpose

Poly normally plans and executes each command immediately. This milestone adds
an explicit deferred mode for users who need several independently authored
commands to become one frozen action graph before any action runs:

```bash
poly add repository repo-a --path repo-a --repo https://example.test/repo-a.git --prepare
poly add repository repo-b --path repo-b --repo https://example.test/repo-b.git --prepare
poly plan
poly exec
```

The ordinary iterative workflow remains the default. `--prepare` is explicit,
there is only one current prepared plan, and `poly exec` executes that exact
persisted plan without replanning.

Commands accumulated in the current plan add canonical ordering constraints
only when they overlap structurally or target the same resources. An added
child also requires the manifest constraint produced by its newly added parent.
Independent work remains eligible for bounded parallel execution. Provider
diagnostics that depend on the original request are preserved, while graph
diagnostics are recomputed over the complete accumulated plan.

## Command contract

```text
poly <verb> ... --plan       preview one isolated plan
poly <verb> ... --prepare    append to the current prepared plan
poly plan                    display the current prepared plan
poly plan clean              discard its disposable generated state
poly exec                    execute the frozen current plan
```

The special `poly init <root-repository> <target>` workflow remains immediate
or preview-only. It rejects `--prepare` without cloning because recursive
hydration depends on inspecting the newly cloned root and therefore cannot be
part of an exact frozen plan without runtime expansion.

The former `poly plan <verb>` expert form is removed. `poly run <verb>` remains
an expert immediate-execution form, but it cannot bypass a current prepared
plan.

Preparation persists only generated `.poly/` state. Authored `poly.yaml`,
`poly.lock.yaml`, `.gitignore`, repositories, services, and external systems are
unchanged until execution. A successful execution consumes the current plan and
retains its historical run report. A failed execution retains both documents
for diagnosis.

## Canonical persistence

The current plan uses the existing `poly.state/v1` envelope containing one
`poly.report/v1` plan document. Its normalized requests and frozen actions are
part of that document; there is no parallel batch language, command script, or
intention file. The plan identifier remains a content fingerprint, not a name
or a selector exposed by `poly exec`.

The persisted base fingerprint covers authored workspace composition. Every
append and execution verifies it. A changed base produces an actionable stale
diagnostic rather than implicit replanning.

## Driver-contributed add façades

`add` is an engine-owned construction verb, but its specialized vocabulary is
provided by drivers:

```text
poly add module ...
poly add repository ...
poly add postgres ...       # possible external contribution
```

Drivers register façade names, argument schemas, and a pure translation to the
canonical planning request. The registry validates identities and collisions in
deterministic order. The engine builds dynamic help and dispatches the selected
facade without knowing a closed list of technologies.

Driver registration also rejects façade names and flags reserved by the engine,
such as `workspace`, `--workspace`, `prepare`, and `--prepare`. An invalid
installed contribution is therefore isolated before parser construction and
cannot prevent the Poly CLI from starting.

The system constructor contributes `module`; the Git driver contributes
`repository`. Blueprints, logical pathless services, and environment bindings
remain later concerns.
