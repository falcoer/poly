# Poly 0.12.3 — Deferred command preparation and planned UX

Status: **validated**. This document is the authoritative detailed scope; the
[roadmap](../../ROADMAP.md#0123--deferred-command-preparation-and-planned-ux)
is its compact index.

Validation was explicitly supplied after acceptance of the complete 0.13
runtime. The final integrated state passed 235 tests with 90.25% coverage and
GitHub Actions run `34137233314` on commit
`0b37958f04fa5c0ac69e4cd088321512ed263d01`. The annotated milestone tag is
created on the documentation commit that records this explicit validation.

## Purpose

Poly 0.12.2 proved that several commands can be assembled and executed as one
plan. Field acceptance also showed that resolving and freezing the complete
action graph after every `--prepare` call makes large batches unnecessarily
slow and presents a prepared command too much like completed work.

0.12.3 records normalized commands immediately and performs one workspace
inspection and one whole-graph resolution when `poly exec` starts. The graph
is still frozen and persisted before its first action executes.

## Interactive contract

A prepared command is rendered as planned work, not successful work:

```text
ADDING 405-core-service-test-src from <url> (ref: P17)
 ○ Planned (81 commands prepared in current plan)
```

The planned result is magenta and the authored command heading uses the default
foreground color. Singular and plural command counts are rendered correctly.
No action count, executable status, frame, reminder, or changing plan
fingerprint is shown during preparation. The final compact presentation was
refined and accepted with 0.12.5 without changing the 0.12.3 journal semantics.

## Execution order

`--prepare` performs syntax and façade validation and atomically records the
normalized command without driver inspection or planning. `poly plan` displays
that ordered command journal. `poly exec` then snapshots and inspects the
workspace once, resolves the complete command set, persists the resulting frozen
action graph, and executes it.

Resolution failure is side-effect free and retains the journal and diagnostics.
Successful execution consumes the journal and retains the frozen historical
plan and run report.

## Compatibility

Existing 0.12.2 frozen prepared plans remain executable or cleanable. They
cannot silently acquire the new deferred-resolution semantics when another
command is appended.

## Implementation evidence

The 0.12.3 implementation introduces a versioned prepared-command journal,
defers workspace inspection and action planning to `poly exec`, freezes the
resolved graph before execution, and preserves the legacy 0.12.2 frozen-plan
reader. Acceptance coverage includes provider bypass during preparation,
planned-only CLI rendering, ordered multi-command execution, repository batch
preparation without authored-file mutation, execution against the current
workspace snapshot, and atomic retention on resolution conflict.
