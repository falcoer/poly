# Poly 0.12.5 — Terminal rendering modes and durable history

Status: **planned**. The authoritative scope and acceptance criteria are
maintained in [the roadmap](../../ROADMAP.md#0125--terminal-rendering-modes-and-durable-history).

## Purpose

The current interactive renderer repeatedly moves the cursor upward and repaints
every known action row. That strategy works only while the complete dynamic block
remains inside the visible terminal viewport. Once output spans multiple screens,
cursor addressing cannot reach primary scrollback lines and repeated repainting
leaves duplicated or damaged history. Periodic elapsed-time refresh makes this
failure repeat even when no action changes.

Version 0.12.5 replaces that implicit behavior with two explicit presentation
modes and establishes the serialized terminal contract required by 0.13 parallel
execution.

## Rendering modes

### Paginated live mode

`live` is selected automatically only when stdout is interactive and Poly can
conservatively establish cursor addressing, isolated-screen support, terminal
width, and terminal height. The renderer enters an isolated terminal screen,
draws only a viewport-sized page, and never rewrites the primary scrollback.

The page capacity is computed from visual rows after wrapping, reserving space
for the command context, page indicator, and progress row. When actions span
multiple pages, the renderer automatically follows current activity and displays
the current and total page numbers. Keyboard navigation and a general-purpose TUI
are outside this milestone.

### Append-only flow mode

`flow` is used for redirected output and any terminal that does not satisfy the
live capability contract. The explicit `--flow` option also selects it on a
capable terminal.

Flow output never emits cursor-addressing or alternate-screen sequences. During
execution it appends each action only when that action reaches a terminal state.
It does not persist transient `RUNNING` rows.

## Final historical view

On every live exit path, Poly first prevents further timer and action repaint,
then restores and resets the primary screen, and finally renders a complete flow
history from canonical action results. The history contains:

- the user-facing command heading;
- exactly one terminal row per planned action in canonical plan order;
- the final command summary and aggregate timing;
- user-facing file and URL output references.

The final history is generated from result data rather than copied from the live
screen. It is therefore complete, scrollable, and independent of pagination.

## Timestamp presentation

Successful, failed, and blocked action rows end with their completion time:

```text
✓ OK       repository-a (git/hydrate) · cloned [2026-09-04 14:03:10]
```

The live progress row ends with the current time while retaining elapsed duration:

```text
IN PROGRESS [██████────] 4/10 actions · 40 % · 00:00:05 [2026-09-04 14:03:15]
```

Every human-readable timestamp uses square brackets, second precision, and the
process-local timezone. Structured reports preserve existing UTC ISO-8601 values
with millisecond precision and do not adopt the presentation-only format.

## Serialized terminal ownership

One dispatcher owns all terminal writes. Action workers, driver handlers, native
progress integration, and elapsed-time producers publish events; none writes
directly. The dispatcher applies synchronized sequence order and renders from an
immutable latest-state snapshot.

Clock refresh is represented as a timer event in the same queue. Shutdown first
closes event admission, drains or rejects events according to the exit policy,
marks the renderer closed, clears native progress, restores terminal state, and
only then emits final history. No timer repaint can race with completion output.

This is the compatibility boundary for 0.13: parallel execution may change event
arrival timing, but it cannot create a second terminal writer.

## Capability and fallback policy

Automatic live selection is deliberately conservative. Missing height, dumb
terminals, CI, redirection, unsupported cursor control, or unsupported isolated
screen handling select flow. Capability detection records width and height and
does not infer support merely from color capability.

Failure to enter or maintain live mode must restore any partially changed
terminal state and continue safely in flow mode.

## Verification strategy

Verification includes:

- renderer state-machine transitions and immutable snapshots;
- multi-page plans under deliberately small terminal heights;
- visual-line accounting for wrapping, ANSI color, and wide Unicode;
- alternate-screen entry, restoration, reset, and exceptional cleanup;
- live-to-history output with exactly one row per action;
- explicit and automatic flow selection without cursor controls;
- completion and progress timestamps, local-time conversion, and structured UTC
  parity;
- synchronized races between action events, timer ticks, interruption, and
  finish;
- native OSC progress ownership and cleanup;
- redirected output and Windows/Linux behavior;
- POSIX pseudo-terminal integration coverage where available.

String-buffer assertions alone are insufficient for viewport behavior; tests must
also model terminal height and validate the interpreted screen/transcript state.

## Exclusions

Version 0.12.5 does not implement parallel scheduling, keyboard-driven paging, a
full-screen TUI toolkit, configurable display timezones, or changes to canonical
event persistence.
