# Poly 0.13.2 — Configuration generation and Eclipse preparation

Status: **implemented; CI and Eclipse real-use acceptance pending**.
Prerequisite: accepted 0.13.1 contracts.

## Implemented profile and boundary

The first supported profile is **navigation**: one general Eclipse project at
`.eclipse/.project`, with portable linked folders for existing selected workspace
subdirectories. It supports heterogeneous compositions, including Git and Maven
observations of the same directory. It does not configure Java/m2e/PDE classpaths,
launches, preferences, working sets or installation. This bounded choice was
recorded before implementation; importing a Java project remains separate.

The bundled `eclipse` driver uses only `poly.driver` and `poly.model`. Its ordinary
`configure` planner and execution handler use the accepted API 1.1; there is no
projection registry or new generation protocol. The `configure:eclipse` facade
normalizes intent. Dynamic driver verbs can expose their registered facades;
`poly run <verb>` remains the generic entry point. No additional blueprint is
introduced for the single fixed navigation profile.

`poly.eclipse.json` is created once as user-owned shared intent, recording the
profile/schema version, project name and selected node IDs. Changing that file
changes the next desired configuration. Runtime state is not the durable source.
The generated XML includes an in-file SHA-256 marker over its exact XML body;
existing unmarked files and modifications invalidate ownership and are refused.
There are no managed sections and no automatic removal. Other files remain
user-owned. Machine-local Eclipse state is not emitted.

Planned actions declare both output paths through `file/write` claims and carry
exact contents, mutations, input hashes and linked directories in the serializable
`POLY_ECLIPSE_CHANGES` payload. Unchanged outputs are not rewritten. Handlers check
the frozen inputs and directories before writing, use exclusive creation and
atomic replacement per file, and report delivered files through normal outputs.
An invalid targeted configuration proposes a blocked action requiring the missing
`eclipse/configuration/valid` fact and an explained rejection; it never triggers
an implicit prerequisite verb. Direct execution of this blocked action also fails.

The profile is saved first; delivery failures expose any already delivered output
and can be retried by replan. There is no global rollback or interprocess lock
against external editors. Symlinks and Windows junctions along involved paths
are rejected. Close the Eclipse project while regenerating.

See the [cookbook](../cookbook/eclipse.md) for preview, generation, Eclipse import,
ownership, recovery and safe manual removal. Real-use acceptance must verify the
linked folder navigation and refresh behavior in the user's Eclipse installation.

Local validation (2026-09-09): Ruff formatting/lint, strict mypy on 57 files,
315 tests passed in the full run, total coverage 90.78%, and wheel/sdist build.
The subsequent concise blocked-plan diagnostic improvement passes 53 focused
Eclipse/reporting tests and strict typing. SDK CLI validate/inspect/
determinism pass; meaningful generation determinism is separately verified with
populated Git/Maven node fixtures, because this planning-only driver does not
produce its own inspection inventory. CI also runs the suite on Windows.

## Purpose

Prepare an existing workspace for Eclipse, continuing the Oomph-replacement
objective and proving generation as an ordinary driver operation.

## Scope

- Implement an Eclipse technology driver through the public plugin SDK.
- Select a useful bounded preparation profile from the actual workspace:
  project selection/import preparation, preferences, and launch configurations
  are candidates; record the exact supported subset before implementation.
- Use a facade for normalized preparation intent and the minimal blueprint only
  where a reusable profile adds value. Do not require a blueprint for every file.
- Define ownership of generated files, user files, and managed sections; declare
  outputs, affected paths, preconditions, conflicts, and execution resources.
- Provide reviewable planned changes, deterministic content, no-op regeneration,
  and a diagnostic for incompatible/manual modifications. Tool-specific merging
  stays in the driver. A stale plan must not silently overwrite intervening edits.
- Define provenance and any safe removal policy without relying on .poly as the
  sole durable record of user intent. Keep shared and machine-local settings distinct.
- Expose generation failures and delivered files through normal action results.
- Document preparation and use in the cookbook.

## Acceptance

A representative existing workspace can be prepared and opened in Eclipse using
the documented supported profile. Repeating generation leaves unchanged files
unchanged; customization outside the managed scope survives. Collisions and stale
inputs fail with actionable evidence. Windows paths and supported POSIX behavior
are verified, required CI is green, and real-use acceptance is recorded.

## Exclusions

Installing Eclipse/JDKs, full Oomph feature parity, global preference replacement,
unbounded configuration merges, runtime plan expansion, and a separate projection
registry or generate protocol. Automated launch is not implied.
