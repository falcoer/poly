# Poly 0.13.2 — Configuration nodes and Eclipse hydration

Status: **in progress — foundational correction implemented; real Eclipse import pending**.
The milestone must not be tagged or closed before real-use acceptance.

## Correction delivered

- Removed the bundled navigation-only Eclipse driver and its standalone command.
  There is no compatibility alias or application dispatch added to the engine.
- Added pathless configuration nodes, root-owned YAML persistence, driver-owned
  versioned schemas, and reusable `add` facade translation.
- Made source inspections and workspace coherence explicit hydration actions.
  Availability and inspection facts order them within the fixed plan; projections
  consume a consolidated inventory through the public SDK.
- Kept manual natures and recorded per-driver observation provenance.
- Limited Maven hydration scans to the root POM and explicit module descriptors.
- Migrated the independent Eclipse contract fixture to `add` then `hydrate`.
  It generates a request document only; it does not claim a real Eclipse import.
- Revised Driver/Extension API to 2.0 for the nullable node path contract.

The [implemented contract](../architecture/configuration-hydration.md) defines
selection, failure, validation, persistence and compatibility precisely.

## Remaining work

1. Implement and package the real external Eclipse driver and Equinox adapter.
2. Import actual projects with their names and required JDT/m2e/PDE natures;
   preserve existing descriptions and use supported Eclipse APIs.
3. Describe and validate shared plugin settings, project settings, tools and
   variables, with explicit local binding of machine-dependent values.
4. Apply the working-set convention and reconcile membership via Workbench APIs.
5. Verify idempotent hydration, collisions, partial failure/retry, supported
   product/plugin versions, Windows and POSIX against a real Eclipse installation.
6. Record both onboarding paths and real-use acceptance before the milestone tag.

The local runtime currently has Java but no Eclipse installation. Core and
contract tests are evidence for the finite workflow, not evidence for headless
Eclipse behavior. See [the import design](../architecture/eclipse-workspace-import.md).

## Migration

The previous unreleased navigation prototype is removed, including its tests and
bundled registration. Previously generated `poly.eclipse.json` and `.eclipse`
files in user workspaces are not read, converted, or deleted automatically. Review
and remove those local artifacts after preserving any user modifications. Nothing
from them is required by the new configuration-node contract.

and wheel/sdist build pass. The onboarding test creates and commits a control
repository, clones it into a second root, then hydrates both from the same locked
source commit. Eclipse runtime acceptance is still pending.
