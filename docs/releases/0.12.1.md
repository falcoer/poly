# Poly 0.12.1 — Stable interactive CLI presentation

Status: **implemented-awaiting-ci**. The authoritative scope and acceptance criteria are
maintained in [the roadmap](../../ROADMAP.md#0121--stable-interactive-cli-presentation).

The implementation is available for functional review from the retained
`poly-0.12.1-distributions-<commit>` CI artifact. Validation still requires a
green complete CI run, merge to `main`, and the annotated milestone tag on the
accepted commit.

The milestone marker advanced to 0.12.2 before this tag was emitted. Recovery
therefore uses a forward validation commit containing the unchanged 0.12.1
contract and subsequent prepared-plan safety corrections; it does not infer a
historical validation from a later run. The complete CI must pass on that exact
commit before creating `roadmap/0.12.1-interactive-cli`.

## Purpose

The default terminal view must read as one command block rather than as an
append-only event trace. It must preserve the hierarchy between the user's
request, Poly's generated plan, individual actions, and the final command
outcome while retaining timestamped execution evidence in canonical reports.

This milestone is also the presentation prerequisite for 0.13: the rendering
state must be capable of maintaining more than one live action row even though
0.12.1 keeps execution sequential.

## Target default terminal view

```text
────────────────────────────────────────────────────────────────────────
ADDING 401-validator-conf-src from https://web-qp-scm.arcelormittal.com/qualitycontrol/401-validator-conf-src (ref: master) ...
        PLAN     bb6075d0da956f4fccc3 · 2 action(s) · executable
                ✓ OK       git.resolve:401-validator-conf-src (git/resolve-source)
                           · resolved master to d5976c78951f4a8815394a9ecd500351cd730977
                ✓ OK       construct.add:401-validator-conf-src (poly/construction/add)
                           · added node '401-validator-conf-src'
────────────────────────────────────────────────────────────────────────
        ✓ SUCCESS  poly add · 2 succeeded
────────────────────────────────────────────────────────────────────────
```

The horizontal rules delimit the whole command and therefore have no
indentation. The request heading also begins at the left margin. `PLAN` and
the final result share the first indentation level, actions use the second, and
wrapped action details use the third.

The heading uses the terminal's default foreground color. This is intentionally
not forced ANSI white: a terminal with a light theme must remain readable.
`PLAN` remains cyan, and terminal action and command states keep their
semantic success, failure, warning, and neutral colors.

## Source-aware request headings

For a source-backed add, the heading represents authored user intent:

```text
ADDING <node-id> from <source-url> (ref: <requested-ref>) ...
```

The URL and requested selector come from `poly.source.url` and
`poly.source.ref`. They must be sanitized before display and must never expose
embedded credentials. The requested selector belongs in the heading; the
resolved immutable commit belongs in the Git action result.

Commands without a source retain their existing concise heading. Local-source
and adoption requests use an equivalent unambiguous representation without
inventing a remote URL or reference.

## Stable action rows

On an interactive terminal, `RUNNING` is a transient visual state. The
renderer owns a stable row for the action and replaces that row with its final
`OK`, `KO`, or `BLOCKED` representation. The completed view therefore
contains exactly one row per action.

Drivers, action handlers, and child processes never own the terminal. Process
stdout and stderr are captured in an action-isolated channel, handlers return a
structured execution result, and one serialized renderer consumes runtime
events and owns every terminal write. The rendering state is keyed by action
identifier and retains canonical plan order even when completion events arrive
in another order.

Although execution remains sequential in 0.12.1, tests inject interleaved
`running` and terminal events for several actions. This proves that replacing
one row cannot overwrite another and prepares the exact rendering path used by
the bounded-parallel executor.

A non-interactive or append-only destination cannot safely replace prior
content. At normal verbosity it emits only terminal action rows and never emits
cursor movement, erase sequences, or color controls not explicitly requested.
Verbose modes may expose additional diagnostics and process output, but must not
duplicate the normal completed action row.

Structured output is not a terminal transcript. JSON, YAML, and XML retain the
complete event history without terminal control sequences.

## Structured driver result channel

A driver execution result has three distinct information channels:

- one optional concise scalar value for the action row;
- zero or more typed user-facing output references;
- structured details and captured stdout/stderr for diagnosis and persisted
  reporting.

A scalar value is a JSON-compatible string, number, or boolean, optionally
paired with a short label. It must be representable on one terminal line and
must not contain control or terminal escape sequences. Examples include a
resolved version, a project key, a boolean check, or a quality metric:

```text
        ✓ OK       sonar.version (sonar/query-version) · 10.7.0
        ✓ OK       quality.coverage (sonar/query-metric) · coverage: 82.4 %
```

Arbitrary driver text is not a scalar value. Multiline explanations belong in
structured details, captured logs, or an explicitly generated report.

An output reference is canonical data with a `file` or `url` kind, a target,
and optional label and media type. A driver returns one only for a deliverable
that the command explicitly requests or exposes. Internal run files, captured
logs, temporary resolutions, and implementation artifacts are not promoted to
user-facing outputs.

The built-in inspection command provides a direct acceptance path for file
outputs without impersonating a driver action:

```shell
poly inspect --format json --output reports/inspection.json
```

The generated canonical report contains its own top-level output reference and
the terminal completion exposes the same file below `OUTPUT`. Without
`--output`, inspection retains its existing behavior.

The renderer aggregates output references from all action results in canonical
plan order and removes exact duplicates. Valid diagnostic output produced by a
failed action remains visible below the failed command result:

```text
────────────────────────────────────────────────────────────────────────
        ✓ SUCCESS  poly quality-report · 2 succeeded
        > OUTPUT
              D:\test\quality-report.html
              https://sonarqube.example/report/16787434
────────────────────────────────────────────────────────────────────────
```

On a compatible interactive terminal, the visible path or URL is wrapped in a
safe OSC 8 hyperlink. A Windows file target uses a normalized `file:///` URI
while retaining its native path as the visible label. Unsupported terminals,
redirected streams, and CI logs receive identical plain text without escape
sequences. JSON, YAML, and XML preserve the output kind, target, label, and media
type as data.

Values, labels, paths, and URLs are sanitized before rendering. Control
characters and terminal escapes are rejected, URL credentials are never
displayed, and hyperlink targets cannot inject terminal commands.

## Timing contract

A persisted transition is useful only when its occurrence can be placed in
time. Every run event therefore carries:

```json
{
  "sequence": 4,
  "state": "running",
  "action_id": "git.resolve:401-validator-conf-src",
  "occurred_at": "2026-09-02T12:41:08.317Z"
}
```

`occurred_at` is an RFC 3339 UTC timestamp. The sequence remains the total
ordering key and resolves equal timestamp values. Each action result also
exposes `started_at`, `completed_at`, and `duration_ms`. Duration must be
measured with a monotonic clock even though the externally reported instants use
the wall clock.

These values make the event history diagnostically useful and provide the
evidence needed to measure action overlap in 0.13.

## Terminal behavior

The terminal sink, layout calculation, and semantic rendering remain separate:

- semantic rendering decides headings, labels, indentation, and colors;
- layout calculates usable width, wrapping, and stable row extents;
- the terminal sink decides whether in-place updates and hyperlinks are
  supported;
- the serialized renderer is the only component allowed to write to or
  reposition the interactive terminal.

For interactive iTerm2 and Windows Terminal sessions outside CI and tmux, the
terminal sink also publishes native plan progress through `OSC 9;4`. The value
is derived from the number of terminal actions in the frozen plan: success uses
the normal state, blocked actions use warning, and failures use error. Poly
clears the native indicator on completion and interruption. Other terminals and
captured output receive no progress escape sequences.

Every interactive terminal with cursor updates also receives one portable plan
progress row below the stable action rows. Its bar adapts to the available
width, reports the completed action count and percentage, and reflects warning
or failure state. The renderer removes this transient row before printing the
final summary; append-only and structured output remain unchanged.

Horizontal rules use the current usable width with a deterministic fallback for
captured output. Resizing, long identifiers, wide Unicode characters, failures,
runner exceptions, and interruption must not leave partial control sequences or
corrupt following shell output.

## Compatibility

This milestone does not change planning or execution semantics. Quiet and
verbose levels, `--color auto|always|never`, and `NO_COLOR` retain their
documented meaning. Additive timing, scalar-value, and output-reference fields
are emitted consistently by every canonical structured renderer and covered by
schema-parity tests. Existing drivers that return only `success`, `summary`,
and `details` remain compatible.
