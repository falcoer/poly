# Poly 0.13.1 — Executable specification and parity baseline

Status: **pending**. This milestone starts only after the validated Python
0.13 implementation and does not itself implement the Rust port.

## Purpose

Poly 0.13 is now the accepted executable reference for planning, extensions,
bounded scheduling, reporting, rendering, and recovery. Before another language
can implement those contracts safely, 0.13.1 must turn the observable Python
behavior into a compact, versioned, language-neutral conformance baseline.

The goal is not byte-for-byte imitation of Python internals. It is semantic
parity at every durable boundary that users, plugins, automation, or persisted
state can observe.

## Objectives

### 1. Freeze durable schemas and identities

Document and version canonical fixtures for:

- `poly.yaml` and `poly.lock.yaml`;
- prepared command journals and frozen plans;
- plugin, contribution, node, action, resource, and plan identities;
- run events and JSON, YAML, and XML reports;
- compatibility and rejection behavior for unknown schema versions.

The fixtures must contain data only. Persisted plans must not contain callbacks,
implementation objects, Python import paths used as identity, or scheduler state.

### 2. Build a black-box conformance corpus

Provide deterministic scenarios that exercise the installed `poly` command as
a user would, including:

- direct and prepared execution;
- `--jobs 1`, explicit parallel limits, and `--jobs auto`;
- deterministic frontiers and exclusive resources;
- independent overlap, failure, exception, blocked descendants, and interruption;
- output isolation and global causal event sequencing;
- `live`, `flow`, plain text, JSON, YAML, and XML output;
- Windows and POSIX path, CPU-capacity, signal, and process behavior;
- built-in and external contributions resolved only by stable identity.

Concurrency proofs use barriers or controlled runners, never timing thresholds
alone. Comparisons normalize volatile values such as temporary paths, process
identifiers, wall-clock timestamps, and elapsed duration.

### 3. Add a differential parity runner

Create one harness that can run the same corpus against a selected Poly
executable and compare normalized semantic results. It initially certifies the
Python implementation against its own golden fixtures; a future Rust executable
must pass the identical harness without privileged exceptions.

The runner compares canonical documents, exit behavior, state transitions, and
event partial order. ANSI bytes, terminal width adaptation, and raw timings are
tested separately where they are part of the public presentation contract.

### 4. Record the compatibility policy

Classify observable behavior as:

- stable and required for parity;
- versioned and migratable;
- presentation-only and intentionally flexible;
- internal and not part of the compatibility contract.

Any intentional incompatibility must require a schema or protocol decision and
cannot be hidden inside a new implementation.

### 5. Capture a reproducible performance baseline

Add synthetic public fixtures representative of the validated 81-repository
workflow and record preparation, `--jobs 1`, and bounded-parallel measurements.
The baseline detects material regression but does not make correctness depend on
machine-specific timing. No private repository, URL, credential, or workstation
state is copied into the test corpus.

## Acceptance

- every durable format has a versioned canonical fixture and schema owner;
- the Python distribution passes the black-box corpus on Windows and Linux;
- the parity runner can target an arbitrary executable without importing its
  implementation modules;
- tests prove scheduling and isolation semantics deterministically;
- the compatibility classification is reviewed and linked from the architecture
  document;
- the performance fixture and measurement method are reproducible;
- the complete existing quality, clean-room, external-driver, and acceptance CI
  remains green;
- a real-use validation confirms no regression before the milestone is tagged.

## Excluded

- implementing or shipping the Rust port;
- changing plan semantics or adding user-facing orchestration features;
- marketplace or network plugin installation;
- interprocess plugin transport, distributed execution, preemption, adaptive
  weighting, or driver-internal parallelism;
- weakening built-in/external driver parity or transferring scheduler ownership
  outside Poly core.

## Validation marker

The future annotated tag is `roadmap/0.13.1-executable-specification`. It must
not be created, and the milestone must not be marked `validated`, until all
acceptance checks and explicit real-use validation are complete.
