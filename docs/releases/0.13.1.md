# Poly 0.13.1 — Contribution contracts and finite preconditions

Status: **implemented-awaiting-validation**.
Revised: 2026-09-09. This scope replaces the former executable-specification and
Rust-parity baseline. Implementation is complete on the development branch;
real-use acceptance and complete remote CI remain required.

Session entry point: [2026-09-09 handover](../handover/2026-09-09-next-step.md).

## Purpose

Protect the validated Python baseline and prepare useful configuration plugins.
Preserve the current flexible applicability model rather than replace it with a
central election language. Follow [ADR 0002](../decisions/0002-python-contributions-and-tool-configuration.md).

## Scope

1. Document existing inspect/propose/execute and facade translate entry points,
   plugin discovery, stable contribution identities, and legacy compatibility.
   Distinguish API role, declared driver capability, supported verb, and node nature.
2. Formalize driver attribution of observed natures and reconciliation with
   authored natures. Poly selects by verb; drivers decide applicability using
   natures and other domain context. Keep creation and multi-node aggregation.
3. Specify non-applicability versus rejected candidates and preserve actionable,
   bounded diagnostics in heterogeneous selections.
4. Audit requires/produces and initial facts, including the graph/runtime mismatch
   for initial facts and multiple producers. Document the chosen semantics and
   correct only demonstrated inconsistencies, with focused regression coverage.
5. Define the minimal blueprint data contract using one Eclipse configuration
   example: identity/version, parameter validation, desired configuration,
   resource references, and required contributions. Record how Poly resolves it
   before freezing a plan. No general template engine or executable blueprint hooks.
6. Specify the minimal facade generalization beyond add and its canonical output.
   Retain dict[str, str] compatibility; implement only changes required to exercise
   the contract fixture. Do not freeze a speculative user command syntax.
7. Document compatibility expectations for manifests, lock, prepared journals,
   plans, reports, and contributions. Reuse existing serialization/acceptance tests;
   no comprehensive cross-language golden corpus.
8. Reuse existing cold/warm inspection benchmarks and quality hooks. Identify actual
   coverage/workflow gaps before adding tests or tooling.

## Acceptance

- Current Git/Maven and prepared workflows preserve their observable behavior.
- An independent plugin fixture proves the minimal facade/blueprint boundary
  without privileged scheduler/renderer access; it is not a production IDE driver.
- Nature-driven acceptance and rejection remain domain-owned and tested where
  coverage is missing; no mandatory supports() or central nature filter.
- Prerequisite semantics cover missing producers, initial facts, cycles, alternate
  producers, and failed producers consistently between planning and execution.
- Blueprint and facade decisions identify implemented versus reserved API surface.
- Existing required quality and Windows/Linux CI gates remain green; affected
  Ruff/type/test checks are run before publication.
- Documentation and cookbook explain the preserved behavior; explicit real-use
  acceptance occurs before marking the milestone validated.

## Exclusions

Rust/Node/Java core rewrites, parity runner, IPC, marketplace, dynamic plan expansion,
automatic prerequisite synthesis, new scheduler, production tool drivers, and
duplicating already validated cache/logging/parallelism work.
