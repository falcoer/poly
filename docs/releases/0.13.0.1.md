# Poly 0.13.0.1 — Targeted execution performance and actionable diagnostics

Status: **pending**. This corrective milestone follows the validated 0.13
parallel scheduler. It restores the usefulness of targeted daily commands in
large workspaces without changing planning or execution semantics.

## Purpose

On a real workspace containing hundreds of Maven projects, a command such as:

```text
poly build --select maven:021-container-management/_container-management-parent/linux-docker-java21
```

currently performs a complete fresh inspection before applying the selection.
The resulting cold-start cost can exceed the actual targeted Maven invocation.
It also runs process actions from the workspace root even when the selected
Maven reactor has its own execution context. This loses reactor-local Maven
configuration such as `.mvn/maven.config` and can change plugin behavior (for
example Docker host resolution).

At the same time, a failed command persists its stdout and stderr correctly but
the ordinary terminal result neither shows a useful error excerpt nor points to
the persisted files. Repeated Maven ambiguity diagnostics also hide the
actionable fact and their locations.

Poly must make the selected scope, inspection freshness, action outcome, and
failure evidence immediately understandable.

## Objectives

### 1. Preserve the explicit action execution context

Add a serializable working-directory field to the canonical action contract.
The runner must resolve it beneath the workspace, reject an invalid or escaping
path, and execute the command in that directory.

The Maven planner must set this field to the selected reactor root. Therefore a
Poly Maven action observes the same reactor-local `.mvn/` configuration,
relative paths, plugin setup, and process context as the equivalent manual
Maven invocation. The working directory participates in canonical action and
plan identity.

### 2. Persist and reuse a deterministic inspection inventory

Persist the canonical inspection inventory beneath `.poly/` with enough
version and file-state information to determine whether it is valid.

For commands with an explicit selection:

- reuse a valid inventory rather than reparsing every Maven POM;
- invalidate the affected inventory deterministically when a relevant workspace
  manifest, POM, local Maven relationship, driver version, or inspection schema
  changes;
- rebuild safely when no valid cache is available;
- retain a deliberate refresh path for diagnosis and recovery;
- ensure cached and fresh inspection produce the same canonical inventory,
  diagnostics, planned actions, plan ID, and exit behavior for unchanged input.

The cache is an implementation detail and remains disposable with `.poly/`.
It must never make an outdated model silently executable.

### 3. Make targeted scope visible

For a Maven verb, the concise plan and run header must distinguish:

- implicit whole-workspace selection;
- explicit selected node IDs;
- applicable Maven project count;
- resulting Maven reactor action count.

The display must state the default scope when no `--select` is supplied.
It must not list hundreds of node IDs in ordinary or single-verbose output.

### 4. Provide actionable inspection diagnostics

Group duplicate inspection diagnostics by stable cause. For an ambiguous Maven
coordinate, the concise output must state once:

- the coordinate;
- the number and identities of competing local definitions;
- the number of affected local references;
- a deterministic way to obtain the detailed locations.

The canonical JSON, YAML, and XML report retains every individual diagnostic
and location. Detailed text output must remain bounded and readable.

### 5. Expose command failure evidence

Each executed action already persists `stdout.txt`, `stderr.txt`, and
`details.json` in its isolated action directory. On failure, Poly must:

- show the exit code and a bounded, safe excerpt of the meaningful stderr;
- expose stdout, stderr, and details as explicit output references in the final
  text report;
- make the same references available through `poly report <run-id>`;
- preserve full process output in canonical structured reports and the isolated
  files;
- avoid printing unbounded logs or secrets merely because a command failed.

A successful action keeps the existing compact output unless it explicitly
returns domain outputs.

## Non-negotiable behavior

- inspection and planning remain read-only, deterministic, and side-effect free;
- a process action executes only in its explicit, workspace-contained working
  directory; no controller infers one from its current process directory;
- cache reuse does not change node identity, action identity, plan identity,
  dependency closure, Maven `-am` behavior, or scheduler admission;
- a missing, unreadable, incompatible, or invalid cache falls back safely to a
  fresh inspection;
- failure presentation does not alter process exit codes or canonical reports;
- all paths and excerpts are rendered safely on Windows and POSIX terminals.

## Acceptance criteria

- a Maven action planned for a reactor runs with that reactor as its working
  directory and observes its `.mvn/maven.config`;
- a fixture with reactor-local Maven configuration produces the same command
  outcome through Poly and a manual Maven invocation from the reactor;
- invalid, escaping, and missing action working directories fail safely before
  process execution;
- a warm explicitly selected Maven build avoids a complete POM reparse when no
  relevant input changed;
- modifying a relevant POM or workspace manifest invalidates the cache and
  yields the same plan as a new process with no cached inventory;
- fresh and cached planning fixtures are semantically identical;
- benchmark fixtures record cold and warm preparation time separately from Maven
  execution, without making correctness depend on a machine-specific threshold;
- `poly build` states implicit versus explicit scope and Maven module/reactor
  counts in concise text output;
- an ambiguity affecting many references renders one concise grouped warning
  while structured formats retain all locations;
- a failing subprocess reports exit code, bounded error excerpt, and concrete
  `stdout.txt`, `stderr.txt`, and `details.json` output references;
- `poly report <run-id>` exposes the same failure evidence after the fact;
- tests cover cache validity, invalidation, report compatibility, diagnostic
  grouping, stdout/stderr persistence, Windows paths, and terminal width limits;
- Ruff, strict mypy, full tests with coverage, build packaging, external-driver
  conformance, and complete Windows/Linux CI are green;
- real-use validation is performed on a large multi-repository workspace before
  tagging.

## Exclusions

- changing Maven dependency-policy semantics or implicitly selecting additional
  project roots;
- inheriting an arbitrary controller process working directory instead of the
  action's declared workspace-relative context;
- remote cache sharing, daemon processes, watch mode, or distributed execution;
- changing the parallel frontier scheduler, retry, cancellation, or controller
  contracts;
- replacing Maven output with a custom build protocol;
- weakening canonical structured reports in favour of terminal-only rendering.
