# Poly 0.13.0 — Bounded parallel plan execution

Status: **planned**. The authoritative scope and acceptance criteria are
maintained in [the roadmap](../../ROADMAP.md#013--bounded-parallel-plan-execution).

## Purpose

Poly already negotiates a finite immutable plan and derives ready actions from
monotonic `requires` and `produces` constraints. Version 0.13 executes
independent actions from the same ready frontier concurrently without weakening
that model, allowing hydration, verification, and independent technology jobs
to use the capacity available to the machine.

Parallelism is an executor policy. It must not change the negotiated action
set, action order, plan identifier, or allow the executor to invent work.

## Frontier execution

At the beginning of an execution iteration, the executor takes a snapshot of
all actions whose requirements are satisfied. This canonically ordered set is
the current frontier.

Only actions in that snapshot may be admitted during the iteration. When the
frontier contains more actions than the worker limit, unscheduled members remain
queued as workers become available. On each admission, the scheduler scans the
remaining canonical tuple and selects the first action compatible with resources
currently held. A busy repository therefore does not stall an unrelated one.
Constraints produced by successful actions are collected, but the next frontier
is not opened until every action in the current frontier reaches a terminal
state.

The frontier barrier provides a deterministic definition of “same plan level.”
It deliberately avoids allowing a newly eligible dependant to overtake an
independent action that was already ready.

## Worker limit

The command line supports:

```text
poly <verb> --jobs 1
poly <verb> --jobs 4
poly <verb> --jobs auto
```

`--jobs 1` preserves the observable sequential 0.12.1 behavior.
`--jobs auto` uses the CPU entitlement or affinity visible to the Poly process
and falls back conservatively to one worker when it cannot determine that
capacity. An explicit positive value remains bounded by applicable controller
or policy limits. Planning and action-catalog commands do not accept `--jobs`.

Every controller declares a positive `parallel_capacity`; legacy descriptors
default to one. Poly enforces the global worker limit and a separate semaphore
for every selected controller. With several selected controllers, their summed
capacity bounds the effective global limit while each individual capacity still
applies.

The requested mode, requested value when present, and effective worker count are
recorded in the run report together with controller capacities. They do not
participate in the frozen plan fingerprint.

## Execution resources

Planning `ActionClaim` values arbitrate which provider owns an operation and
scope. They are not runtime locks and must not be overloaded with a second
meaning.

Driver API 1.1 adds a defaulted `parallel_safe` flag and the exclusive execution
resources an action touches,
such as:

- `workspace:manifest`;
- `workspace:lock`;
- `repository:<node-id>`;
- `reactor:<path>`;
- `run-output:<action-id>`.

Two ready actions requiring the same exclusive resource do not overlap. An
action that does not opt in cannot overlap any other action. Structural actions
are always serialized. API 1.0 drivers remain supported and receive these
conservative defaults.

Each action receives a stable, traversal-safe subdirectory beneath
`<run-directory>/actions/`. `${POLY_RUN_DIRECTORY}` resolves to that directory.
Concurrent stdout, stderr, structured details, and outputs are associated with
their action and never share an unsynchronized output file.

Parallel-safe in-process handlers use action-scoped output sinks from their
execution context or return structured data. They must not mutate or redirect
process-global stdout and stderr. Existing handlers retain legacy stream capture
and remain serialized.

## Failure semantics

The existing semantics remain authoritative:

- a failed action produces none of its declared constraints;
- only actions depending on missing produced constraints become blocked;
- independent siblings continue;
- work already running is not cancelled merely because a sibling failed;
- runner and driver exceptions are contained as failure of their own action.

Final action results retain canonical plan order. Workers return immutable
completion records to a single scheduler thread. That thread publishes events,
updates constraints, and assigns the synchronized global sequence, preserving
actual admission and scheduler-observed completion chronology.

On user interruption, the 0.13 `drain` policy stops admitting queued actions and
lets admitted work finish. Never-started actions become `cancelled`, the run
becomes `interrupted`, and Poly persists a reloadable report. Forced preemption
and cooperative cancellation are outside this milestone. A second interrupt may
terminate the client, but Poly must not claim that a complete report was saved.

## Canonical report

The additive `run.execution` object records the execution policy and frozen
frontiers without changing `poly.report/v1`:

```json
{
  "jobs": {"requested": "auto", "effective": 4},
  "interruption_policy": "drain",
  "controllers": [{"name": "local", "parallel_capacity": 8}],
  "frontiers": [
    {"sequence": 1, "action_ids": ["git:verify:a", "git:verify:b"]}
  ]
}
```

An explicit requested worker count is a JSON number. Frontier membership is
canonical; event timestamps and action durations demonstrate actual overlap.

## Interactive rendering

The 0.12.1 terminal renderer owns one stable row per admitted action. Several
rows may simultaneously show `RUNNING`; each is replaced in place when its
action terminates. The portable progress row and native `OSC 9;4` state track
total completed actions across frontiers. Once a frontier completes, only its
final action rows remain.

Append-only and structured destinations do not emulate cursor movement.
Timestamped canonical events remain the source of truth for reconstructing
concurrent execution.

## Verification strategy

Tests use synchronization barriers and controlled runners to prove overlap;
they do not rely only on elapsed-time thresholds. Coverage includes:

- canonical frontier membership and admission order;
- worker-limit enforcement and automatic capacity fallback;
- per-controller capacity enforcement;
- mutually exclusive resource serialization;
- overlap of independent actions;
- failed producer and independent-sibling behavior;
- runner exception and drain-interruption containment;
- synchronized event sequencing and timestamp coherence;
- action-specific output and path isolation;
- API 1.0 and `--jobs 1` compatibility;
- Windows and Linux terminal and structured-report parity.

The functional demonstration hydrates or verifies several independent
repositories concurrently while serializing operations that address the same
repository. The persisted timestamps show real overlap and permit comparison
with the same plan executed using `--jobs 1`.

## Exclusions

Version 0.13 does not introduce distributed scheduling, speculative execution,
preemption, cooperative cancellation, adaptive CPU/memory or I/O weights,
driver-internal thread pools, cross-process fairness, or runtime plan expansion.

The implementation contract and rationale are recorded in
[ADR 0002](../decisions/0002-bounded-parallel-execution.md).
