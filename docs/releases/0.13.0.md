# Poly 0.13.0 — Bounded parallel plan execution

Status: **planned**. The authoritative scope and acceptance criteria are
maintained in [the roadmap](../../ROADMAP.md#013--bounded-parallel-plan-execution).

## Purpose

Poly already negotiates a finite immutable plan and derives ready actions from
monotonic `requires` and `produces` constraints. Version 0.13 executes
independent actions from the same ready frontier concurrently without weakening
that model, allowing hydration, verification, and independent technology jobs
to use the capacity available to the machine.

Parallelism is an executor policy. It must not change the negotiated action
set, action order, plan identifier, or allow the executor to invent work.

## Frontier execution

At the beginning of an execution iteration, the executor takes a snapshot of
all actions whose requirements are satisfied. This canonically ordered set is
the current frontier.

Only actions in that snapshot may be admitted during the iteration. When the
frontier contains more actions than the worker limit, unscheduled members remain
queued in canonical order as workers become available. Constraints produced by
successful actions are collected, but the next frontier is not opened until
every action in the current frontier reaches a terminal state.

The frontier barrier provides a deterministic definition of “same plan level.”
It deliberately avoids allowing a newly eligible dependant to overtake an
independent action that was already ready.

## Worker limit

The command line supports:

```text
poly <verb> --jobs 1
poly <verb> --jobs 4
poly <verb> --jobs auto
```

`--jobs 1` preserves the observable sequential 0.12.1 behavior.
`--jobs auto` uses the CPU entitlement or affinity visible to the Poly process
and falls back conservatively to one worker when it cannot determine that
capacity. An explicit positive value remains bounded by applicable controller
or policy limits.

The requested mode, requested value when present, and effective worker count are
recorded in the run report. They do not participate in the frozen plan
fingerprint.

## Execution resources

Planning `ActionClaim` values arbitrate which provider owns an operation and
scope. They are not runtime locks and must not be overloaded with a second
meaning.

An action may instead declare the exclusive execution resources it touches,
such as:

- `workspace:manifest`;
- `workspace:lock`;
- `repository:<node-id>`;
- `reactor:<path>`;
- `run-output:<action-id>`.

Two ready actions requiring the same exclusive resource do not overlap.
Structural actions and command-less driver handlers that have not explicitly
declared concurrency safety remain serialized for backward compatibility.
Drivers may opt actions into concurrency only through the public SDK contract.

Each action receives isolated process-output and driver-detail storage beneath
the run directory. Concurrent stdout, stderr, and structured details are
associated with their action and never share an unsynchronized output file.

## Failure semantics

The existing semantics remain authoritative:

- a failed action produces none of its declared constraints;
- only actions depending on missing produced constraints become blocked;
- independent siblings continue;
- work already running is not cancelled merely because a sibling failed;
- runner and driver exceptions are contained as failure of their own action.

Final action results retain canonical plan order. Timestamped events retain
actual start and completion chronology, and their synchronized global sequence
provides a total order.

On user interruption, the executor stops admitting queued actions, applies an
explicit termination policy to running work, records final or interrupted
states, and persists a reloadable report. It must never silently abandon a
running action while reporting the run as complete.

## Terminal event and rendering contract

Version 0.13 depends on the validated 0.12.5 terminal rendering state machine.
Workers and action runners never write to the terminal. They publish timestamped
transitions to one synchronized dispatcher, which assigns the global sequence
and is the sole producer of text and OSC terminal output.

The paginated `live` renderer consumes immutable state snapshots and may show
several `RUNNING` rows simultaneously without addressing the primary terminal
scrollback. Timer ticks use the same event path as action transitions. Completion,
interruption, and renderer shutdown are serialized so that no repaint can occur
after terminal restoration begins.

`flow` remains append-only and emits terminal actions in observed completion
order during execution. After a live run, the renderer restores the primary
screen and emits exactly one canonical-plan-order historical view. Structured
destinations retain all timestamped events and remain the source of truth for
reconstructing actual concurrent chronology.

## Verification strategy

Tests use synchronization barriers and controlled runners to prove overlap;
they do not rely only on elapsed-time thresholds. Coverage includes:

- canonical frontier membership and admission order;
- worker-limit enforcement and automatic capacity fallback;
- mutually exclusive resource serialization;
- overlap of independent actions;
- failed producer and independent-sibling behavior;
- runner exception and interruption containment;
- synchronized event sequencing and timestamp coherence;
- action-specific output isolation;
- `--jobs 1` compatibility;
- Windows and Linux terminal and structured-report parity.

The functional demonstration hydrates or verifies several independent
repositories concurrently while serializing operations that address the same
repository. The persisted timestamps show real overlap and permit comparison
with the same plan executed using `--jobs 1`.

## Exclusions

Version 0.13 does not introduce distributed scheduling, speculative execution,
preemption, adaptive CPU/memory or I/O weights, driver-internal thread pools, or
runtime plan expansion.
