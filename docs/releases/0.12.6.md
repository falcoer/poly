## Purpose

Version 0.12.6 is an architectural milestone inserted before 0.13. Its purpose is to make the plugin the stable unit of extension while preserving the current driver behavior and preparing the runtime for bounded parallel execution and a later Rust implementation.

This milestone is structural, not a plugin marketplace project. It must not introduce download catalogs, remote installation, process isolation, or a complete cross-language transport.

## Plugin as extension container

A Poly plugin is the container for versioned contributions:

```text
Plugin
├── metadata
├── drivers
├── facades
├── blueprints
└── optional resources
```

The initial implementation may contain only existing driver and facade contributions. Blueprints may remain absent or minimal, but the registry model must already reserve them as a first-class contribution type.

Existing built-in and external drivers remain compatible and may be represented as contributions owned by implicit or explicit plugins.

## Registries

Introduce two distinct concepts:

- `PluginRegistry`: discovers and validates plugin containers and their compatibility with the Poly Extension API;
- `ContributionRegistry`: indexes contribution identities and resolves drivers, facades, and blueprints independently of their implementation language or packaging mechanism.

Contribution identities must be stable and serializable so that plans and actions never depend on in-process Python object identity.

## Poly Extension API invariants

The existing Driver API becomes the first subset of a more general Poly Extension API. The following invariants are normative:

- extensions do not depend on Poly core internal structures;
- actions, requests, contributions, diagnostics, outputs, and results crossing the extension boundary are serializable;
- Poly alone owns plan lifecycle, validation, dependency resolution, scheduling, parallelism, retry, timeout, cancellation, persistence, event ordering, reporting, and terminal rendering;
- drivers do not imperatively call other drivers or recursively invoke the scheduler;
- extensions never write directly to the terminal renderer;
- workspace access is exposed through a controlled read view rather than a mutable engine object;
- requested workspace mutations are returned as contributions and are validated and applied by Poly;
- built-in and external contributions share the same functional contract; in-process execution is an optimization, not a privileged semantic API.

The governing rule is: extensions know their domain; Poly owns orchestration.

## Drivers

Drivers inspect technology-specific state, contribute executable actions, and execute only actions explicitly assigned to them.

A driver must not control frontier selection, concurrency, retries, cancellation, renderer state, or action admission. Driver-internal parallel orchestration is outside the contract unless explicitly introduced by a later milestone.

## Facades

Facades become first-class plugin contributions using the same Extension API boundary.

A facade translates a user-facing high-level command into normalized intent or planning contributions. It must not imperatively orchestrate Poly, invoke other drivers directly, mutate the workspace, or execute nested plans.

## Blueprints

Blueprints are first-class plugin contributions under the same container and registry model.

Blueprints should be primarily declarative. If later evolution requires executable hooks, those hooks must use the same public Extension API and return validated contributions without access to scheduler or core internals.

A blueprint may describe desired structure or composition; drivers remain responsible for technology-specific executable actions.

## API versus transport

The logical Extension API and the future transport protocol are separate concerns.

0.12.6 defines the logical contract only. It must not commit Poly to a specific IPC implementation. A later transport may use stdio/JSON-RPC, gRPC, sockets, WebAssembly, or another mechanism without changing extension semantics.

This separation must allow a future Poly core to host or communicate with contributions implemented in Rust, Python, Java, TypeScript, Go, or other languages.

## Compatibility and migration

No current user-facing driver behavior should change solely because of this milestone.

The migration path is incremental:

1. model current drivers as plugin-owned contributions;
2. resolve driver and facade identities through `ContributionRegistry`;
3. preserve current Driver SDK compatibility;
4. expose plugin ownership and contribution inventory through canonical inspection/reporting;
5. reserve blueprint contribution registration without requiring blueprint functionality yet.

## Acceptance criteria

- all existing built-in/system/external driver tests remain valid;
- existing driver manifests can be adapted or wrapped without behavioral changes;
- a plugin descriptor exposes id, version, Poly API compatibility, contributions, and optional dependencies;
- duplicate plugin and contribution identities fail deterministically;
- driver and facade resolution occurs through the contribution registry rather than a hard-coded engine inventory;
- plan/action persistence does not contain Python callbacks or runtime object references;
- plugin ownership is observable in structured inventory;
- facades cannot gain privileged scheduler access;
- the public contract leaves room for blueprint contributions without requiring their execution model to be implemented now;
- the complete Windows/Linux quality, typing, test, packaging, and external-driver conformance matrix remains green.

## Exclusions

0.12.6 does not implement:

- plugin marketplace or public catalog;
- network installation or automatic updates;
- plugin sandboxing or trust policy;
- complete multi-process or remote-driver transport;
- distributed execution;
- blueprint catalog aggregation or template engine;
- bounded parallel execution, which belongs to 0.13.

## Relationship to 0.13 and Rust

0.13 must build on this extension boundary. The parallel scheduler must consume stable actions and contribution identities without knowing how a driver was packaged or which language implements it.

The validated Python implementation at the end of 0.13 is the intended executable specification for any subsequent Rust port. A Rust implementation must reproduce the public contracts and externally observable semantics rather than translate Python code line by line.

See [Plugin Extension API and Rust migration boundary](../architecture/plugin-extension-api-and-rust.md).

## Implemented public surface

The Python implementation exposes `Plugin`, `PluginRegistration`,
`PluginRegistry`, `ContributionDescriptor`, and `ContributionRegistry` through
the public `poly.driver` package. Legacy `DriverRegistration` factories remain
valid and are adapted into implicit plugin containers. Explicit plugin packages
can use the `poly.plugins` entry-point group, while existing `poly.drivers`
entry points continue to load unchanged.

Canonical inspection and driver reports now include plugin descriptors,
contribution identities, and the owning plugin for every loaded driver. Driver,
facade, and reserved blueprint lookup is performed by `ContributionRegistry`.
