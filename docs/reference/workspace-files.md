# Workspace files contract

This document defines the implemented version 1 authored files for a Poly workspace.
It is normative for milestones 0.8 through 0.12.

## Architectural invariants

1. The workspace root node owns `poly.yaml`.
2. The root Git repository versions the workspace composition, not the content of
   independently versioned child repositories.
3. `poly.yaml` is the only authored source of truth for composition.
4. `poly.lock.yaml` records the reproducible resolution of materialized child
   sources. It never replaces intent expressed by `poly.yaml`.
5. `.poly/` contains only generated, disposable local state. Removing it must
   not prevent reconstruction from the root repository.
6. A node identifier is stable across construction, inspection, planning,
   execution, selection, and reporting. Drivers enrich that node; they do not
   create a second identity for it.
7. Poly never introduces Git submodules unless a future explicit feature requests
   them. Child repositories are ordinary independent checkouts.

## `poly.yaml`

Location: `<workspace-root>/poly.yaml`.

The file is UTF-8 YAML and is committed in the root repository. Unknown fields
are rejected for a known schema version. Paths are slash-separated, relative to
the workspace root, must not escape it, and are compared with platform-aware
collision checks.

### Version 1 shape

```yaml
schema: poly.workspace/v1

workspace:
  id: quality-control
  name: Quality Control
  root-node: root

nodes:
  - id: root
    kind: workspace
    path: .

  - id: service-api
    parent: root
    kind: repository
    path: workspace/service-api
    source:
      driver: git
      url: https://git.example.com/quality/service-api.git
      ref: develop

  - id: frontend
    parent: root
    kind: repository
    path: workspace/frontend
    source:
      driver: git
      url: https://git.example.com/quality/frontend.git
      ref: main

  - id: service-api-reactor
    parent: service-api
    kind: module
    path: .
    natures:
      - maven/reactor
```

### Fields

| Field | Required | Meaning |
|---|---:|---|
| `schema` | yes | Exact schema identifier, initially `poly.workspace/v1`. |
| `workspace.id` | yes | Stable workspace identifier. |
| `workspace.name` | no | Human-readable label. |
| `workspace.root-node` | yes | Identifier of the single root node. |
| `nodes[].id` | yes | Stable unique identifier chosen by the author or by `poly add`. |
| `nodes[].kind` | yes | `workspace`, `repository`, `module`, or a future schema-defined kind. |
| `nodes[].parent` | except root | Parent node identifier; the graph must form one rooted tree. |
| `nodes[].path` | yes | Path relative to the parent node. `.` denotes the parent's own root. |
| `nodes[].source` | no | Materialization request owned by the named driver. |
| `source.driver` | with source | Driver identifier, initially `git`. |
| `source.url` | for Git clone | Repository URL; credentials must never be embedded. |
| `source.ref` | no | Requested branch, tag, or commit; driver policy defines the default. |
| `nodes[].natures` | no | Author assertions or hints, validated and enriched by inspectors. |

A repository is a source-control boundary. A module is a technical unit inside
a repository. They are not synonyms: one repository can contain several Maven
modules, and a module does not imply another Git checkout.

Drivers may discover undeclared technical modules and persist them as
observations in `.poly/state`. A discovered child repository not present in
the manifest is marked `observed-only`; it does not silently become part of
the reproducible composition.

## `poly.lock.yaml`

Location: `<workspace-root>/poly.lock.yaml`.

This file is generated by Poly and committed in the root repository. It is
human-readable but must be changed through an explicit resolution operation.
The root repository is not locked inside its own lock file, avoiding a
self-referential commit.

### Version 1 shape

```yaml
schema: poly.workspace-lock/v1
manifest-digest: sha256:0123456789abcdef...

sources:
  service-api:
    driver: git
    url: https://git.example.com/quality/service-api.git
    requested-ref: develop
    resolved:
      commit: a31bc42fceaf...
      ref-kind: branch

  frontend:
    driver: git
    url: https://git.example.com/quality/frontend.git
    requested-ref: main
    resolved:
      commit: 97de1204c981...
      ref-kind: branch
```

### Lock rules

- `manifest-digest` covers the canonical semantic content of `poly.yaml`, not
  comments or the lock file itself.
- `sources` is keyed by the stable node identifier from `poly.yaml`.
- Git entries record the normalized source URL, requested reference, immutable
  resolved commit, and resolution kind.
- `poly init` uses the lock by default and verifies the final checkout HEAD.
- `poly add --repo` resolves `source.ref` and atomically records its exact commit
  without creating or changing the declared child path.
- `poly hydrate` materializes sources only from their immutable lock entries; it
  does not reinterpret a moving selector. Its interactive text view flushes the
  frozen plan before materialization and action state changes as they occur;
  structured reports remain emitted only as complete canonical documents.
- Missing, stale, or inconsistent lock data is a diagnostic. Poly does not
  silently move a locked checkout.
- `poly update` resolves requested refs, safely materializes and verifies the
  resulting commits, then rewrites the lock. `poly lock --from-workspace`
  explicitly adopts clean local `HEAD` commits.
- Secrets, credentials, machine-specific paths, cleanliness, and local branch
  state never belong in the lock.

## Root `.gitignore`

Poly manages a delimited block in the root repository's existing
`.gitignore`, preserving all user-owned lines outside that block.

```gitignore
# BEGIN poly managed
/.poly/
/workspace/service-api/
/workspace/frontend/
# END poly managed
```

The managed block contains `/.poly/` and the exact root-relative paths of
declared child repository nodes, including paths not yet hydrated. It does not ignore `poly.yaml`,
`poly.lock.yaml`, the complete workspace root, or unrelated sibling content.
Exact child paths are preferred over a broad `/workspace/` rule.

`poly init` creates or reconciles the block. `poly add` adds the new child
path. Removing a node removes only its managed ignore entry. Updates are
atomic, deterministic, idempotent, use forward slashes, and fail with a clear
diagnostic if the managed markers are malformed or duplicated.

This ensures a commit made at the root records the composition files but never
stages independently versioned child worktrees.

## Generated state

The initial generated layout is:

```text
.poly/
  state/
    workspace.json
    inventory.json
  plans/
  runs/
  logs/
```

These files may use canonical JSON. They are rebuildable caches, plans, results,
and observations, never authored configuration. No indispensable composition
information may exist only below `.poly/`.

## Required restoration journey

Given only a clone of the root repository:

1. Poly validates `poly.yaml` and its root-node tree.
2. It validates `poly.lock.yaml` against the manifest.
3. It reconciles the managed `.gitignore` block.
4. It plans visible Git actions for every declared child source.
5. It clones or safely adopts each child and verifies the locked commit.
6. Inspectors enrich the same stable nodes with Git, Maven, and later natures.
7. It rebuilds `.poly/state` and emits the complete job report.

No `poly add` is required during restoration.

During authoring, `poly add --repo` performs only declaration and immutable
resolution. A later explicit `poly hydrate` executes steps 4 through 6 for the
locked child sources.

## Local worktree versus shared lock

The committed lock is the reproducible shared reference, not a continuously
updated mirror of local worktrees. Git clients such as EGit may advance a child
branch independently. Poly preserves that checkout and reports its relationship
to the lock. Interactive commands operate on the observed worktree; locked CI
or restoration can require exact correspondence.

An explicit adoption or update is required before the root repository records a
new shared composition. This prevents silent lock churn while avoiding the false
impression that an older lock is the latest branch state.
